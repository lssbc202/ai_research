# Harness Handbook

> **论文**：Ruhan Wang 等，*Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable*，arXiv:2607.13285v1，2026 年 7 月 14 日。  
> **原文**：[arXiv HTML](https://arxiv.org/html/2607.13285v1)  
> **阅读日期**：2026 年 10 月 10 日

## 一、核心判断

这篇论文解决的是修改智能体运行框架（**harness**）之前的一道难题：**用户描述了想改变的行为，但相关代码究竟在哪里、是否已经找全？** 作者把这个问题称为“行为定位”，并提出 Harness Handbook：为一套具体 harness 生成一份按运行行为组织、能够指回当前源码的手册。编码代理收到修改需求后，先沿手册找候选位置，再打开源码核对，最后制定修改计划。[引言](https://arxiv.org/html/2607.13285v1#S1)

论文的实验支持“手册让代理更容易找对修改位置，并减少规划时使用的 token”。**实验测的是只读规划器给出的定位与修改计划**，没有运行修改后的 harness 来证明其任务能力提高。论文第 3 部分描述了“执行修改并同步手册”的完整流程；自动、自主地反复改进 harness 被放在未来工作中。[实验设置](https://arxiv.org/html/2607.13285v1#S4.SS1) · [结论](https://arxiv.org/html/2607.13285v1#S5)

## 二、为什么需要一份按行为组织的地图

Harness 负责提示词构造、状态管理、工具调用和执行控制。一个看似单一的需求，例如“工具失败后改变下一步动作”，可能同时涉及工具执行、异常处理、共享状态和下一轮决策。自然语言需求以**行为**为单位，仓库却以**文件和函数**为单位；单靠文件名、关键词或局部调用关系，容易漏掉相隔很远的实现位置。[研究动机](https://arxiv.org/html/2607.13285v1#S1)

这种需求与代码结构之间的错位并非 harness 独有。作者选择 harness，是因为运行行为常跨执行阶段，并通过状态衔接；因此手册中特别设有“执行阶段”和“跨阶段状态读写关系”。论文只在两个 harness 上评估，尚未证明同样的设计在一般软件仓库中有相同幅度的收益。[相关工作](https://arxiv.org/html/2607.13285v1#S2) · [表示方法](https://arxiv.org/html/2607.13285v1#S3.SS1)

## 三、方法：手册长什么样，怎么生成，怎么使用

### 3.1 手册长什么样

Handbook 是针对**某个仓库及其当前代码版本**的产物。它有三层：L1 介绍整套 harness 的主循环与整体数据流；L2 介绍各执行阶段的职责、输入输出和依赖；L3 落到具体函数或文件，并保存可核对的源码位置。另有一份跨阶段状态视图，说明重要状态在哪里写入、在哪里读取。使用者先看总览，再逐步打开与当前需求有关的细节。[第 3.1 节](https://arxiv.org/html/2607.13285v1#S3.SS1)

实验中，作者把 Handbook 以 **skill** 形式交给规划代理：`SKILL.md` 说明查阅顺序，配套的总览、阶段索引、状态登记和阶段详情文件承载内容。它既是人可读的文档，也包含供定位与后续同步使用的结构化数据；并非一份适用于所有 harness 的预填通用说明书。[附录 C.3](https://arxiv.org/html/2607.13285v1#A3)

### 3.2 第一版如何生成

生成从现有源码开始。第一步由语言解析器提取函数身份、文件与行号、签名、能解析的调用关系等**静态事实**；解析不出的调用会记录下来，不交给模型猜测。第二步由 LLM 阅读源码和调用上下文，判断文件或函数属于哪个执行阶段，并写出其行为说明。第三步将这些材料整理为 L1～L3 文档和状态视图，再核对每个底层条目能否指回当前源码。无法确认的条目会停用或被显式记录。[第 3.2 节](https://arxiv.org/html/2607.13285v1#S3.SS2) · [附录 A](https://arxiv.org/html/2607.13285v1#A1)

作者提供两种组织粒度：

| 模式 | 起点与最细条目 | 论文中的实例 |
|---|---|---|
| 按函数组织 | 需要一份可靠的执行阶段初始提纲；最细条目是函数或连续代码区域 | Terminus-2 |
| 按文件组织 | 先给文件写用途卡片，再从卡片和调用关系推断执行阶段；最细条目是文件 | Codex |

这里要区分两种“检查”：LLM 可以审查归类是否符合代码行为；确定性程序则检查文件、函数、代码范围与源码证据是否对应。**代码位置可验证，不代表每句自动生成的功能解释都得到了形式化证明。**[附录 A.2～A.3](https://arxiv.org/html/2607.13285v1#A1)

### 3.3 收到修改需求后怎么用

论文把找位置的过程叫 **BGPD**（行为引导的渐进式披露）。它的输入是修改需求、该仓库的 Handbook 和**当前源码**。代理先从总览和阶段索引确定相关阶段，再沿共享状态关系补查其他阶段，进入具体函数或文件，沿调用关系扩展候选，最后打开源码核对。输出是一组有证据的候选修改位置：文件路径、可能的函数或区域，以及当前源码片段。**BGPD 本身不改代码。**[第 3.3.1 节](https://arxiv.org/html/2607.13285v1#S3.SS3)

后续规划器根据这些证据写出修改计划；独立的执行器负责应用计划。若仓库出现实际代码差异，系统重新解析受影响源码，并尽量只更新受影响的手册内容；只有原有阶段结构不再适用时才扩大到重建。用于判断“手册哪里过期”的是**实际 diff**，而非计划声称改了什么。源码始终是最终依据。[第 3.3.2～3.3.3 节](https://arxiv.org/html/2607.13285v1#S3.SS3)

附录 E 给出一个直观例子：将“连续两次标记完成才评分”改为“连续三次”。Handbook 中的状态读写关系提醒规划代理，除了主循环中的判断，还要检查初始化和每次运行前的重置。代理随后回到真实源码确认这些位置，再给出修改计划。[附录 E](https://arxiv.org/html/2607.13285v1#A5)

## 四、实验设计与主要结果

作者选取 Python 的 Terminus-2（6 个源码文件）和 Rust 的 Codex（2,267 个源码文件），各设计 30 条不透露目标位置的行为修改请求，覆盖现有行为调整、跨文件能力增加，以及关键词搜索不易找到的路径。两组使用相同的需求、仓库、规划模型和只读工具；差别是能否访问 Handbook 及其导航指引。规划器使用 DeepSeek-V4-Pro；GPT-5.5、Opus 4.8 和 DeepSeek-V4-Pro 三位模型评委分别从定位准确、范围控制和论证质量评分，权重依次为 50%、25%、25%。作者另以两个独立参考计划比较文件与符号级的定位重合度。[第 4.1 节](https://arxiv.org/html/2607.13285v1#S4.SS1) · [附录 C](https://arxiv.org/html/2607.13285v1#A3)

| Harness | 无手册的计划胜率 | 有手册的计划胜率 | 每条需求平均规划 token：无手册 → 有手册 |
|---|---:|---:|---:|
| Codex | 28.3% | **38.3%** | 10.2 万 → **8.9 万**（减少 12.7%） |
| Terminus-2 | 26.7% | **45.6%** | 5.8 万 → **5.3 万**（减少 8.6%） |

这里的“胜率”来自两种计划的逐题比较，含平局，所以两列胜率无需加总为 100%。使用 Handbook 后，与参考计划比较的文件级、符号级召回率、精确率和 F1 均提高；F1 提升范围为 **5.0～18.8 个百分点**，完全找错位置的比例也没有上升。Terminus-2 的绝对定位表现更高，而 Codex 中的提升幅度随参考模型与指标变化明显。[第 4.2 节](https://arxiv.org/html/2607.13285v1#S4.SS2)

## 五、如何评价这篇论文

**最有价值的设计**是把“找全修改位置”单独拿出来处理，并将行为说明、跨阶段状态关系、源码定位和变更后同步放进同一套机制。它与读文件、搜索代码等工具相配合：工具负责访问源码，Handbook 提供针对当前仓库预先整理的导航信息。[第 3 节](https://arxiv.org/html/2607.13285v1#S3)

**证据边界也很清楚：**

1. 实验只评分**定位与修改计划**。论文描述了执行和同步算法，但未用最终任务正确率或修改后的功能测试证明端到端收益。
2. 参考修改位置由模型生成，计划质量也由模型评审；这些指标可以比较两组规划输出，不能直接等同于人工确认的完整正确答案。
3. 对照组有读文件、文件内搜索和列目录工具，但论文没有与更强的项目索引、语义检索或其他专用 MCP/skill 做全面比较。因此不能得出“所有代理都必须配 Handbook”的结论。
4. 报告的 token 节省是**每次规划**的消耗。初次生成、长期维护 Handbook 的成本没有被纳入这一规划指标。是否划算，取决于仓库规模、修改频率和现有工具的质量。
5. 两个仓库分别使用不同的手册组织粒度，论文也未在普通软件项目上测试。因此现有结果不能分离“仓库差异”与“组织粒度差异”，也不能证明方法只适用于 harness。

以上第 2～5 点是根据论文评测协议作出的解读；第 1 点是论文明确说明的实验范围。[实验设置与指标](https://arxiv.org/html/2607.13285v1#S4.SS1) · [附录 C.3](https://arxiv.org/html/2607.13285v1#A3)

## 六、最终理解

这篇论文可以概括为：**给一套 harness 的当前源码制作按行为组织的地图 → 修改需求到来时沿地图找全相关代码并回源核对 → 代码变化后更新地图。** 已有实验表明，这张地图能改善两个测试仓库上的定位和计划质量。将它扩展为真正的 harness 自我改进系统，仍需要验证代码执行后的正确性、实际任务收益，以及制作与维护地图的总成本。[结论](https://arxiv.org/html/2607.13285v1#S5)
