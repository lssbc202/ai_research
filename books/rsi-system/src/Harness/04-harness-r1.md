# Harness-R1

**论文**：*Harness-R1: Learning to Edit Executable Runtime Harnesses from Agent Failure Trajectories*  
**来源**：[arXiv:2608.02276v1](https://arxiv.org/html/2608.02276v1)，2026-08-03  
**作者**：Shuai Shao 等  
**阅读日期**：2026-10-10

## 核心结论

这篇论文研究的不是怎样让做任务的 AI 助手直接学得更好，而是怎样**训练另一个模型，使它更擅长根据助手的失败记录修改其运行代码**。作者把这个专门写补丁的模型称为 *harness engineer*，把方法称为 Harness-R1。修改后的运行代码要经受同一批任务的重跑检验，重跑结果再用于更新修改者的模型参数。在 WebShop、ALFWorld 和 DBBench 上，原始 Qwen3.5-9B 助手的三项平均成功率由 44.3% 提高到 53.6%。

本文的关键区别是**学习“如何提出修改”**。许多已有方法也会搜索、筛选或迭代修改 harness，但负责提出修改的模型通常保持不变；Harness-R1 让这个修改者从补丁的实际执行效果中学习。

## 一、论文要解决什么问题

一个工具型助手做任务时会留下完整过程：它看到了什么、作出什么动作、工具或环境如何回应、最终是否成功。这些记录能暴露重复犯错的模式，例如过早执行动作、丢失任务状态、误用接口或陷入无效循环。仅修改模型权重是一条改进路线；论文选择修改模型周围的可执行运行代码，即 *harness*。

这里的 harness 具体指组织上下文、向环境转发动作、检查动作、接收反馈并触发恢复的代码。**目标助手**是模型加上这套基础运行代码；主要实验中的目标模型是 Qwen3.5-9B。**修改者**也是一个独立的 Qwen3.5-9B 模型，按固定提示读取失败记录并输出规定格式的代码补丁。它不参与后续任务求解，也不调用任务环境的工具。训练时更新的是修改者的参数，目标助手的模型参数保持冻结。〔§3.1；附录 A、B、C〕

## 二、方法：从失败到可验证的补丁

流程是：让原助手先完成一批任务 → 从失败任务中提取约束、关键动作与反馈，形成“失败包” → 修改者生成可复用补丁 → 验证补丁能否安装 → 将补丁单独装入目标助手 → 让目标助手重做**整批任务，包括原本成功的任务** → 用前后任务结果之差评价补丁。这样，补救旧失败与破坏旧成功都会进入同一个分数。〔§3.1，公式 1〕

补丁只允许在四个运行节点添加代码：任务开始时设置状态或提示；助手决策前补充信息；助手提出动作后、执行前拦截或改写动作；环境返回反馈后给出恢复提示。补丁需要针对失败中反复出现的规律，不能硬编码某一道题的答案、编号或标识符。无效、没有实际作用或无法完成评估的补丁得 0；能完成评估但降低成绩的补丁得负分。〔§3.1；附录 A、C〕

修改者分两步训练。第一步是监督学习：用 GPT-5.5 提出的候选补丁，经可执行性、完整重跑和“不退步”筛选，得到 **877 个**范例，让修改者先学会写合规补丁。第二步是在线强化学习：针对同一份失败包，从当前修改者采样 **8 个**候选补丁，分别验证和重跑；将八个补丁的收益作组内比较，用 GRPO 更新**修改者**参数。原始任务轨迹和失败包预先缓存，在线阶段重跑的是装入候选补丁后的目标助手。〔§3.2；算法 1；附录 B〕

第 3 部分的公式可以按用途理解：**公式 1**定义补丁收益，即同一批任务安装前后的平均奖励差；**公式 2**是让修改者模仿筛选后范例的监督学习损失；**公式 3**把八个候选补丁的收益转换成相对表现；**公式 4**根据相对表现调整生成补丁的概率，并限制单次更新幅度。算法 1 把“采样—安装重跑—打分—更新修改者”连成训练循环。WebShop 使用环境的连续奖励，ALFWorld 和 DBBench 使用二元成功奖励。〔§3.1–3.2〕

需要注意：八个候选补丁是**同一轮、相互独立的尝试**。论文没有实现补丁跨批次保存、在单个实例里反复修改，也没有实现补丁不断分叉和累积的多代演化。〔§3.1〕

## 三、实验怎么做，结果怎样

三个基准分别考查按要求搜索并购买商品的 WebShop、在文字环境中完成家务操作的 ALFWorld，以及查询和修改数据库的 DBBench。最终测试集分别为 **500、500、300** 个任务。下表列的是**任务成功率**；最右列是三个基准成功率的等权平均，不是把 WebShop 的连续奖励混入平均。〔§4.1；表 1〕

| 方法 | WebShop | ALFWorld | DBBench | 三项平均 |
| --- | ---: | ---: | ---: | ---: |
| 原始 Qwen3.5-9B 与默认 harness | 31.2% | 40.6% | 61.0% | 44.3% |
| 仅监督学习的修改者 | 38.6% | 39.4% | 61.3% | 46.4% |
| Harness-R1 | 42.2% | 53.2% | 65.3% | **53.6%** |
| 直接微调后的目标助手 | 42.6% | 71.2% | 63.7% | 59.2% |
| 微调目标助手 + 为其重新训练修改者 | 43.0% | 84.0% | 65.7% | **64.2%** |

主要结论有三点。第一，只给修改者看优秀补丁范例还不够；继续用补丁的实际任务收益训练，成绩明显更好。第二，目标助手本身变强后，**为这个更强助手重新训练**修改者仍可带来额外 5.0 个百分点的平均提升；这不是同一修改者与目标助手长期交替自动升级的实验。第三，把学到的修改策略用于训练时没见过的 20 种目标模型配置时，每种配置的三基准平均变化均为正；面对由少量失败记录生成补丁、再应用于 1,270 个未见任务的测试，成功率平均提高 **8.9±1.5 个百分点**（三个种子）。〔§4.2–4.4〕

附录里的 WebShop 个案说明补丁如何起作用：目标助手找到合适商品，却在未选择要求的颜色时就购买。补丁在“购买”动作执行前检查必要选项，条件未满足便拦截并提示继续选择。在这个十任务批次中，完全成功的任务从 **2 个增至 5 个**。这只是机制示例，整体效果仍应看上述完整测试集。〔附录 H.1〕

作者还关闭补丁的不同介入位置进行消融。对总体成绩影响较大的，是**动作执行前的检查**和**环境反馈后的恢复**；前者在 WebShop 尤其重要，后者在 ALFWorld 尤其重要。各位置会相互配合，因此消融差值不能简单相加。〔§4.5〕

## 四、怎样看待这篇论文

**主要贡献**是把 harness 修改者本身变成训练对象，并把训练信号绑定到目标助手的实际任务结果。补丁“格式正确”或“解释合理”并不足够，必须在运行中证明有收益。论文用目标模型冻结、相同任务前后重跑、原成功任务也计入评估等设计，让这个信号更具体。〔§3；§5〕

**适用边界**同样明确。训练奖励取自提供失败证据的同一批任务，因此仍可能偏向这批任务；论文做了未见任务测试，但尚未把未见任务退步直接纳入训练目标。现有实验也没有证明部署后无需人工干预地长期自我改进：多轮交替训练目标助手与修改者、补丁跨轮积累、运行成本约束，都是作者列出的后续问题。〔§3.1；§5〕

我的理解是：这篇论文验证了**“写可执行 harness 补丁”可以成为通过结果反馈习得的模型能力**。目前真正被反复训练的是修改者的参数；每次生成的补丁仍是针对当前失败证据的一次性候选方案。若要把它用于持续演化的生产系统，还需要补上跨批次补丁管理、未见任务回归测试和成本控制。这最后一句是基于论文局限作出的工程推论，不是论文已实现的功能。
