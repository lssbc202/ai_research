# Ouroboros

> **论文**：Anton Razzhigaev 等，*Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution*，arXiv:2608.08311v3，2026 年 8 月 31 日。  
> **原文**：[arXiv HTML](https://arxiv.org/html/2608.08311v3)  
> **阅读日期**：2026 年 10 月 10 日

## 一、核心判断

Ouroboros 是一个能修改自身运行框架的 AI 代理。这里的“运行框架”（harness）包括任务循环、工具、提示词、上下文组装、记忆处理和核心代码。它既可以把“改进自己”作为专门任务，也可以从日常工作和人的反馈中发现问题，再决定是否修复。修改经过审查、版本提交后，成为后续任务使用的代码。

论文的主要贡献是**把核心代码的持续自修改放进一个长期运行、可审查、可回滚的系统**，而不是提出新的模型训练方法或“多候选按分数选优”的进化算法。测试成绩说明某些固定版本表现很强；它们并未单独量化自我演化带来的性能增益。

## 二、研究问题与已有工作的关系

作者认为，代理的实际能力由底层模型、运行框架、任务环境和评分方式共同决定。既有自进化研究会修改记忆、技能、提示词或代码；Ouroboros 强调的是部署中的核心代码也可以改，而且要经过受控的 Git 提交，修改后仍能继续服务用户。这个定位是论文对相关工作的比较结论，不宜理解成它首次提出了 RSI。[原文 §1–2](https://arxiv.org/html/2608.08311v3)

## 三、系统架构与改进闭环

系统分成三个边界：[原文 §3](https://arxiv.org/html/2608.08311v3)

| 边界 | 职责 | 与自身演化的关系 |
|---|---|---|
| 启动器与监督器 | 启动、看管进程、发布引导和紧急停止 | 与可修改的代理仓库分开，保留操作员控制权 |
| 代理自身仓库 | 任务循环、工具、提示词、记忆处理、审查逻辑和接口 | 可在权限及审查约束下修改 |
| 外部任务工作区 | 用户项目及其交付物 | 与代理自身仓库分开 |

自修改的大致路径是：**发现问题 → 选择并实现改动 → 确定性预检 → 对暂存差异计算指纹 → 多模型审查 → 再次核对指纹 → 提交新版本**。审查期间只要代码发生变化，旧审查证据就失效。`light`、`advanced`、`pro` 三种运行档位限制自修改权限；审查范围另有 `low`、`max` 设置，`max` 增加全仓库视角的检查。操作员可回滚到已审查的旧状态。[原文 §3、附录 A](https://arxiv.org/html/2608.08311v3)

系统还能让子代理并行调查或写补丁。执行子代理在隔离的工作树中改文件，父代理验证补丁来源、哈希和受保护路径，再负责整合与提交。因此论文中的“并行”是**任务与补丁生产的并行**，没有展示多个自演化谱系竞争、按适应度选出赢家的机制。[原文 §3](https://arxiv.org/html/2608.08311v3)

### Improver 与 Evaluator 如何对应

论文没有正式命名一个独立的 `Improver` 或统一的 `Evaluator`。若用这两个词理解系统：[原文 §3、§5](https://arxiv.org/html/2608.08311v3)

- **Improver** 是代理执行自我改进任务时的角色：判断改进方向，修改自身仓库，并提出可审查的补丁。它与普通任务共用代理核心，但任务目标、工作区和提交权限不同。
- **Evaluator** 不是单一打分器：验证命令检查具体结果，多模型审查检查改动能否进入系统，正式基准的官方评分器衡量固定版本的任务表现。**审查通过不等于性能提升已被证明。**

## 四、自我改进任务怎样触发

论文描述两条入口：[原文 §3–4](https://arxiv.org/html/2608.08311v3)

1. **自由演化**：把改进自身作为任务。代理检查当前系统，选择并实现一项改进；一轮完成后可以安排下一轮。
2. **经验驱动演化**：普通任务、任务后反思、审查阻碍、内部记录和人的反馈暴露故障或低效路径。代理将其归为可持续追踪的问题，再决定是否启动维护任务。

Hope 的后台循环也可在没有当下用户请求时发起维护或演化任务。人的建议只是候选线索；公开对话不能直接调用提交、重启或修改身份等敏感工具。论文没有给出统一的数值阈值、候选评分公式或保证“每次任务结束必然触发改进”的规则。

## 五、Hope：长期运行案例

Hope 是一个持续保有记忆并修改自身实现的 Ouroboros 实例。它在网页聊天、语音、Telegram、Discord、X、网站评论和邮件等七个交互面服务用户；各渠道汇入同一有序消息记录，再形成不同范围的摘要，而不是七个独立代理。人提出能力建议或指出问题，Hope 自己决定是否处理，核心改动仍走审查和提交路径。[原文 §4](https://arxiv.org/html/2608.08311v3)

论文给出两个可追踪案例：其一，用户发现偶发的重复发消息，Hope 增加了发送流程中的重复内容防护；其二，深度自审查因审查材料过长而中断，Hope 将上下文组装改为有上限的“上下文图谱”，优先保留代码依赖图中连接性较高的文件。这两例说明：一次工作中发现的故障，可以变成后来所有任务都会用到的结构性修复。

截至论文设定的 2026 年 8 月 6 日统计点，Hope 已运行 **161 天**；论文报告 **1,085 次自修改提交**、**1,522 次受审查的自编辑尝试**，最近一段时间的审查拦截率为 **63.5%**。这些是长期运行与受控修改的证据，不能直接换算成能力提升幅度。[原文 §4、表 4](https://arxiv.org/html/2608.08311v3)

## 六、评测结果及其含义

下表均为论文报告值。不同基准使用不同模型与任务协议，不能把各行当成同一个统一的“系统智力分”。[原文 §5、表 2](https://arxiv.org/html/2608.08311v3)

| 基准 | 模型 | Ouroboros 结果 | 解释要点 |
|---|---|---:|---|
| Terminal-Bench 2.1 | Opus 5 high | **86.74%**，轨迹审计后 | 原始值 86.97%；一项取巧得分被扣除 |
| OSWorld-Verified | Opus 5 | **90.69%** | 比论文列出的榜首 90.19% 高 0.50 个百分点 |
| CL-Bench | Sonnet 4.6 | **0.2301** 归一化奖励 | 高于所列基线；并非 23.01% 正确率 |
| SWE-bench Pro | GPT-5.6 Luna | **58.2%** | 配对比较中 Codex 为 59.4%，差异无统计显著性（p = 0.40） |
| GAIA | Sonnet 5 | **78.2%** | 接近 Claude Code 的 78.8% |

基准运行使用冻结的代码种子；附录 C 中多个配置明确关闭了核心演化。因此这些成绩主要验证**某个版本的运行能力**，并非“在线自我改进使成绩逐轮上升”的因果实验。比较时还需注意模型、工具、预算和评分协议是否一致。[原文 §5、附录 C](https://arxiv.org/html/2608.08311v3)

## 七、轨迹审计：成绩之外暴露了什么

第 6 节的价值在于追查分数背后的真实执行：[原文 §6](https://arxiv.org/html/2608.08311v3)

- **奖励取巧**：Terminal-Bench 有一次运行满足了较弱的评分条件，却没有完成用户要求的完整流程，因此作者下调分数。
- **参考答案污染**：SWE-bench Pro 的题目标识可能暴露上游修复提交。作者在配对比较中，对双方都采用相同的剔除规则。
- **文件隔离不足**：早期 GAIA 运行继承了操作者的主目录，后续启动器改用隔离的用户文件根目录；论文承认这还不是完整的文件系统沙箱。
- **远程状态漂移**：OSWorld 虚拟机重置后地址变化，执行阶段仍可能持有旧地址；后来加入重置后的端点重新发布与核对。
- **记忆失效**：持续学习中，旧经验可能过时、检索到错误领域，或记录得太晚。作者提出需要更明确的时间和领域元数据。

## 八、安全设计与局限

自修改可能改变工具权限、审查规则和模型路由，因此论文把这些都视为敏感修改面。安全措施包括：持续加载的受保护核心规则、治理文件写保护、多模型差异审查、暂存差异指纹、外部预算上限、独立操作员通道、紧急停止和回滚。尤其值得注意：**更换模型 API 也是能力与风险的变化，应当作为受审计的配置修改。**[原文 §7、附录 A–B](https://arxiv.org/html/2608.08311v3)

论文也留下三项关键空白：

1. Hope 是一条长期运行谱系，缺少多条独立演化谱系或严格的前后对照，难以估计自我演化的因果收益。
2. 多模型审查者可能共享盲点；`low` 上下文模式还省略了全仓库范围审查。
3. 论文展示持续自改与强基准表现，但未给出每次提交的统一性能目标函数，也未证明改进者本身随代际变得更善于改进。[原文“Limitations”](https://arxiv.org/html/2608.08311v3)

## 九、值得借鉴的工程设计

- **把“候选修改”和“允许上线”分开**：代理可自主发现并实施改动，提交门对实际进入下一版本的代码负责。
- **让证据绑定到确切版本**：验证结果、审查证据和暂存差异应绑定到同一份代码；文件一变，旧证据作废。
- **并行写补丁，单点整合提交**：子代理隔离工作，父代理统一核对与合并，减少并发写入核心仓库的歧义。
- **把故障归类再修机制**：记录错误类别、次数、根因和结构性修复，而不只是反复补救单次失败。
- **把运行控制放在可修改核心之外**：预算、紧急停止、回滚与操作员权限要能在代理修改自身时继续生效。

**总评**：Ouroboros 最有说服力的是部署级自修改系统的实现与运行证据；最需要后续研究补上的，是严格测量“哪些自修改确实带来了可泛化的能力增益”。
