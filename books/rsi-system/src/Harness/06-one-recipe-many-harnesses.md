# One Recipe, Many Harnesses

> **一句话结论：**自演化 harness 的主要价值，是从失败记录中找出编程 Agent 反复犯的、可以靠工作规则纠正的错误，并把规则写进提示词、记忆等外部框架。通用工作原则可以迁移，具体构建与测试方法仍要适配语言生态。

- **论文：**Siqi Yang、Qianlan Yang、Yu-Xiong Wang、Saurabh Pujar、Martin Hirzel，*One Recipe, Many Harnesses: What Self-Evolution Encodes Across Languages and Models*，arXiv:2608.10178v1，2026 年 8 月 10 日。
- **原文：**https://arxiv.org/html/2608.10178v1
- **阅读范围：**正文第 1—5 节，以及附录中与方法细节、案例、局限有关的部分。
- **报告日期：**2026 年 10 月 10 日。

## 一、论文要回答什么问题

已有研究表明，让 Agent 观察自己的执行记录，再修改提示词、工具或记忆，常能提高编程任务的通过率。但分数上涨本身解释不了：演化出的内容究竟是通用的工程习惯、某种编程语言的具体知识、对基础模型弱点的补偿，还是对题库的过拟合？

作者把演化流程固定，在 8 种语言和 3 个模型构成的 24 个组合上重复实验，然后同时检查最终成绩与演化文件的内容。论文的重点是**解释 harness 为什么有效、哪些部分可以迁移**；它没有提出新的多路径搜索算法。

这里的 harness 可以理解为 Agent 使用的“工作框架”。模型负责思考和行动；harness 则规定它看到什么提示、何时收到提醒、能调用什么工具、能复用哪些经验。

## 二、方法：TRIAGE 如何工作

作者提出 TRIAGE，一套便于追溯修改原因的外层演化流程。内层 Agent 在仓库里修代码；外层流程读取执行轨迹和评分结果，诊断失败并修改 harness。内层模型的权重不更新。

| 角色或对象 | 职责 | 是否属于被演化的 harness |
|---|---|---|
| 做题 Agent | 阅读仓库、修改代码、运行命令、提交补丁 | 它使用 harness，模型权重保持冻结 |
| Harness | 提示词、工作流钩子、跨题目记忆、工具实现 | **是** |
| 评分器 | 运行基准测试，记录补丁与测试各阶段是否成功 | 否 |
| 诊断器与改进器 | 分析失败，提出并验证 harness 修改 | 否，属于外层 TRIAGE 流程 |

一次演化大致如下：

1. 用当前 harness 在演化题集上运行 Agent，收集操作记录、提交的补丁、评分器各阶段结果和预算使用情况。
2. 诊断失败类型。例如，Agent 修改测试文件导致隐藏测试补丁无法应用；提交的源码无法构建；或提交前没有运行目标测试。
3. 改进器根据证据选择修改位置。长期规则通常写入提示词或记忆；特定时点的干预可写成钩子；需要可执行能力时才考虑工具。
4. 每次修改同时提交一个可检验的“合同”：写明证据、推断的根因、具体修改、预计哪些题会改善、哪些题可能退步。
5. 下一轮重跑演化题集，核对预测与实际结果，选择较好的检查点。选择分数还会惩罚“原来能解、修改后不能解”的题。最终用独立留出题集检验泛化。

论文实际使用**三轮线性迭代**：没有候选种群、分支演化或全局最优搜索。若改动不理想，可以回退到之前的文件版本。这个回退机制只保证在演化题集上按其规则选出较好版本，不能保证留出集一定提高。

### 一个直观例子

在论文给出的 C++ × Claude Haiku 4.5 案例中，初始 Agent 经常同时修改源码和测试文件。评分器随后要应用自己的隐藏测试补丁，结果与 Agent 的测试文件改动冲突，使原本正确的源码修复也得零分。TRIAGE 因此写入“不修改测试文件”的边界规则。这个问题缓解后，诊断重点转向构建和运行目标测试，再补上相应验证步骤。案例展示的是“先找当前最主要的可纠正失误，再逐轮修正工作流程”。

## 三、实验设计与结果

### 实验怎样比较

- **任务：**Multi-SWE-Bench 的仓库级代码修复任务，覆盖 C、C++、Java、Rust、TypeScript、JavaScript、Go、Python。
- **模型：**Claude Haiku 4.5、GPT-5-mini、DeepSeek-V4-Flash。每个组合中，做题 Agent 与外层改进角色使用同一种底层模型，因此主实验的跨模型差异包含两种角色的共同影响。
- **数据：**每种语言抽取 20 道演化题、50 道互不重叠的留出题。留出题不参与修改提案或检查点选择。
- **对照：**简易初始 harness、人工设计的 mini-SWE-agent、三轮演化后的 harness。
- **主要指标：**mean_solve@3，即每道留出题独立运行 3 次后取平均解题率；它不是“三次里任意一次通过”的 pass@3。

### 主要发现

| 问题 | 论文结果 | 通俗解释 |
|---|---|---|
| 演化是否提高成绩？ | 演化版在多数语言 × 模型组合中优于简易初始版；24 个组合里有 14 个达到或超过 mini-SWE-agent。Python 和 GPT-5-mini 是收益接近零的区域。 | 给 Agent 补工作规则常有帮助，但不是每个模型和环境都缺同一套规则。 |
| 收益从哪里来？ | 可自动检测的主要失误包括修改测试文件、提交无法构建的代码、未运行目标测试就提交。不同语言的失误构成明显不同。 | 演化主要让 Agent 更稳定地做对它本来有能力做的步骤。 |
| 演化内容相同吗？ | 不同语言的抽象原则有较大交集，但构建命令、测试路径等具体词汇交集很小；约 20%—40% 的 harness 内容与目标生态直接相关。 | “先验证再提交”可以共用，“怎么构建、跑哪个测试”往往不能照抄。 |
| 能跨语言复用吗？ | 外语种的 harness 移植到目标语言，在 20 个有序组合中有 18 个带来正收益，但 14 个仍不及目标语言本地演化版。 | 通用部分值得复用；复杂生态往往还需本地适配。 |
| 一份通用规则够吗？ | 汇总得到的 10 条通用记忆规则在 Go、JavaScript 上接近本地演化表现；在 Java、C++、TypeScript 上只保留约 48%—68% 的本地增益。 | 通用守则能打底，却会漏掉具体工具链上的关键步骤。 |

跨语言失败的例子尤其清楚：JavaScript harness 写了“提交前运行失败的测试”，却未强调类型检查。搬到 TypeScript 后，测试运行可能成功，代码仍可能通不过单独的类型检查。因此“跑测试”不能自动替代“验证类型或构建”。

## 四、如何理解这些结果

**论文支持的核心判断：**harness 更像一层“执行纠偏器”。模型已有修复问题的潜在能力，但实际执行时会在边界、验证、提交等环节犯错；演化规则减少这些失误，让能力更稳定地转化成结果。作者只在其检测覆盖的失误类型内论证这一点，不能据此断言 harness 永远无法带来新能力。

**本报告的应用判断：**如果要给自己的 Agent 做类似改进，先统计失败究竟集中在哪里，再决定写规则、加钩子还是加工具。应保留独立留出集，并同时观察新解决的题和被改坏的题。跨项目或跨语言复用时，通用习惯可作为起点；构建、测试、类型检查及文件约定需要在目标环境重新核对。

## 五、贡献与局限

这篇论文的价值在于把“自我改进后分数涨了”进一步拆成可追溯的问题：哪类失败触发修改，修改写入了 harness 的哪一部分，哪些原则能迁移，哪些必须依赖目标语言。固定演化配方有助于比较不同语言和模型的产物。

结论也有清楚边界：

1. **任务范围有限。**实验是单次、目标明确的仓库修复；没有验证长时程、多目标或多 Agent 场景。
2. **部分收益依赖评分协议。**“修改测试文件导致零分”与该基准应用隐藏测试补丁的方式直接相关，不能按同样幅度外推到所有实际开发环境。
3. **搜索与样本预算有限。**每个组合仅演化一次、共三轮，且每种语言只有 20 道演化题和 50 道留出题；单个组合的数字存在噪声，得到的是可达到的改进，不是最优 harness。
4. **缺少一些关键对照。**论文未与其他 harness 优化方法做同预算正面对比，也没有检验“把演化开销用于更多直接推理”是否更划算。因此，它证明了相同单次推理预算下 harness 改进有效，尚未证明它是固定总预算的最佳用途。
5. **机制归因不是逐组件完成的。**诊断路由、可证伪修改合同和回退门槛是作为一套方法评估的，论文未分别测出每个组件独立贡献多少。

## 六、读后结论

这篇论文最值得带走的不是某一条万能提示词，而是一个判断顺序：**先辨认 Agent 的可纠正执行失误，再把对应约束写进可修改、可验证、可回退的 harness；复用通用原则时，仍需为目标环境补齐具体工程步骤。**
