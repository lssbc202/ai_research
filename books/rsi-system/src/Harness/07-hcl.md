# HCL

**论文**：Harness Continual Learning: Continual Adaptation Beyond Model Parameters  
**作者**：Borui Kang、Jinrui Gu、Junhan Lv、Wenbin Li（通讯作者）、Lei Wang、Yang Gao  
**机构**：南京大学软件新技术国家重点实验室、University of Wollongong  
**版本与日期**：arXiv:2608.19013v1，2026 年 8 月 19 日  
**原文**：[arXiv HTML 全文](https://arxiv.org/html/2608.19013v1)  
**阅读报告日期**：2026 年 10 月 11 日

## 核心判断

这篇论文研究一种模型外的持续学习：基础模型参数保持冻结，Agent 通过更新提示词、经验记忆、技能和调度规则积累能力。作者把这些长期影响执行的内容统称为 harness，并提出 Harness Continual Learning（HCL）。可以把它理解为：同一个人使用不断改进的工作手册、经验库和操作流程，逐渐能完成更复杂的工作。

论文最值得关注的贡献，是把“更新会不会破坏旧能力”明确放进每次更新的提交条件。新版本必须在当前任务上进步、把历史行为退步控制在预算内，并满足运行约束，才能替换旧版本。它把持续适应组织成一个可拒绝的版本更新流程。

实验支持两个结论：模型参数不变时，harness 的演化仍能改善多个任务序列的最终表现；历史检查的严格程度能调节遗忘。保护越宽松，最终表现却不一定越高。有限历史样例上的零退步也不等于所有旧任务都不会遗忘。

论文实际采用逐组件、逐备选的顺序搜索，没有实现并行多路径演化。论文中的改进器正式名称是 Continual Optimizer；它本身的改进速度是否持续提升，也不在实验所证明的范围内。[对应摘要、§3.3、§4](https://arxiv.org/html/2608.19013v1)

## 研究背景与问题定位

引言和相关工作围绕两条已有研究展开。传统持续学习主要调整模型参数、表示或结构，核心难题是学新知识时损害旧知识。Agent 工程则已经积累了使用工具、保留经验、总结反思、形成技能、自动修改工作流等方法。

作者把两条思路结合起来：把整套可变 harness 当作持续学习状态，观察一连串已部署版本能否获取并保留能力。研究对象包括以前正确的答案、有效的工具调用，以及达到环境目标的行动轨迹。

这里的“遗忘”是行为上的退步。例如，更新记忆后，旧问题检索到的经验变了；修订技能后，以前有效的工具调用步骤变了；修改调度规则后，原来的成功工作流被绕开了。即使模型权重毫无变化，这些问题也可能发生。

四个组件本身来自已有 Agent 系统的常见功能。论文的增量在于将它们共同版本化，并把获取新能力和保留旧行为作为统一目标。[对应§1、§2、§3.1](https://arxiv.org/html/2608.19013v1)

## 方法定义与执行流程

设冻结的基础模型为 $F_\theta$，第 $n$ 次交互时正在使用的 harness 为 $H_n$。一次任务的执行链条为：

原始任务 $u_n$ → 结构化任务 $i_n$ → 组织好的执行上下文 $z_n$ → 结果或行动轨迹 $y_n$ → 执行后反馈 $f_n$。

这些信息合成当前交互证据 $e_n=(u_n,i_n,z_n,y_n,f_n)$。改进器据此提出候选 $\widetilde H_{n+1}$，但候选保持隔离。评估通过时它才成为下一版 $H_{n+1}$；不通过就继续使用 $H_n$。

持续学习的状态是跨任务保存的提示词、规则、记忆和技能。当次任务的结构化输入、上下文和输出属于临时执行产物；只有以获准更新的形式进入持久状态，才会影响后续任务。用于评估的历史锚点集另行管理，不属于运行时 harness。[对应§3.1、附录 A.1](https://arxiv.org/html/2608.19013v1)

## 四个可演化组件

论文将持久状态定义为 $H_n=(I_n,M_n,C_n,R_n)$。四个组件共同决定 Agent 如何理解任务、调用经验和能力，以及安排执行。

### 任务接口

Task Interface $I_n$ 将原始输入变成 $(x_n,g_n,k_n)$：可用信息、任务目标和执行约束。约束可以涉及输出格式、工具使用和环境限制。实现载体包括供模型解析任务的提示词、任务模板，以及解析和规范化规则。

以“找出图片中的红杯子并按指定格式返回位置”为说明性例子：图片是可用信息，定位杯子是目标，返回位置的格式是约束。接口如果只抽取出“描述红杯子”，后续执行即使流畅，也无法完成原任务。因此接口更新会改变后续任务的解释方式，需要随整体 harness 管理版本。

### 经验记忆

Experience Memory $M_n$ 包括两层。Raw Memory 保存具体输入、响应或行动轨迹，以及环境或验证器反馈。论文按任务保留固定数量的交互记录，并采用到达顺序管理，以限制存储量。

Abstract Memory 由模型对原始记录进行归纳，形成带适用范围的指导，例如输出惯例、可靠的推理模式、常见错误。原始记忆保留具体证据，便于复用过去的解决过程；抽象记忆提炼规律，便于迁移到相似任务。

“保存记录”和“把记录归纳成有用经验”是两种不同工作。论文将二者都放进可更新状态，而且附录规定这些持久变化随获准候选一起提交。

### 能力清单

Capability Map $C_n$ 包括外部能力和内部技能。外部能力由运行环境提供，例如 API、检索服务、感知模型、计算器和环境动作。能力条目描述功能、输入输出、调用协议、可用条件和限制。

内部技能从抽象记忆进一步提炼而来：模型把相关经验整理为具有明确输入、输出、执行步骤和适用范围的程序化做法。新技能可以加入，已有技能可以修订。论文表 1 将这一组件的可更新内容具体列为内部技能。

记忆与技能的区别，可以理解为“经验说明”和“可调用做法”的区别。例如，“这类任务常因坐标格式出错”是一条经验；“识别目标、计算坐标、校验范围、按指定结构输出”则更接近可复用技能。这个例子用于解释概念，不是论文展示的具体技能实例。

### 自适应调度器

Adaptive Router $R_n$ 根据结构化任务，从记忆中检索相关经验，从能力清单中选择工具或技能，并把它们组织为执行上下文 $z_n$。模型和外部运行环境随后据此产生结果。

调度器使用模型及其路由提示词、选择标准、工作流模板。它既要在每次任务中选择合适的内容，也允许跨任务修订选择规则。积累了经验和技能，还必须能在恰当时机用上它们，才会改善实际表现。[以上对应§3.2.1—§3.2.4](https://arxiv.org/html/2608.19013v1)

### 共同版本化的意义

四部分不是互不影响的配置。接口改变任务表示，记忆改变可检索的证据，技能改变操作步骤，调度器决定如何组合它们。某个组件单独看更好，组合后的行为仍可能退步。

因此论文将所有拟议变化作为完整候选 harness 管理。最终通过门槛时整体替换；否则候选中的变化不进入已部署状态。这项设计提供了统一的更新边界。[对应§3.2、附录 A.1](https://arxiv.org/html/2608.19013v1)

## 候选生成与受保护的提交

### 改进器怎样生成候选

Continual Optimizer 用提示模板调用冻结的基础模型，将当前 harness 和交互证据提供给它。模型分析反馈，判断哪些组件需要修改，并提出候选内容。这里不是通过梯度训练模型，而是让模型生成外部状态的修改。

多个组件需要修订时，论文采用预定顺序逐个处理。对当前组件生成最多 $K$ 个备选，逐个替换到当前候选中，其他组件保持固定；评估后保留得分最高且达标的备选，作为修订下一组件的基础。如果没有备选达标，该组件保持原内容。已部署版本直到完整候选完成评估并提交后才改变。

这种搜索能提供多种修改方向，但每个组件阶段只保留一个方案。它没有同时保留多个长期演化谱系，也没有报告并行分支的探索算法。[对应§3.3.1](https://arxiv.org/html/2608.19013v1)

### 评估器的三道门槛

新旧版本在相同模型、解码、工具、环境和随机种子条件下比较，提交必须同时满足：

| 门槛 | 定义 | 条件 |
|---|---|---|
| 当前改进 | 当前验证集上的候选表现减去部署版本表现，得到 $\Delta_n$ | $\Delta_n\geq\delta_n$ |
| 历史保留 | 当前版本成功、候选失败的历史锚点数量 $D_n$ | $D_n\leq B_n$ |
| 有效性 | 语法、输出结构、工具使用、任务约束和环境一致性等检查 | 所有适用检查通过 |

多个候选都达标时，评估器依据当前表现、有效性和历史保留的综合分数排序，选择最高分者，平分时随机选择。无人达标就继续使用旧版本。§3.3 给出了硬门槛的公式，但未给出综合排序的明确权重公式；复现时需要进一步明确这一细节。[对应§3.3.2、式 9—13](https://arxiv.org/html/2608.19013v1)

### 历史锚点怎样保护旧能力

每个 anchor 保存过去任务的原始输入和固定成功标准。任务结束时按预定比例选择过去成功和失败的案例，一类不足时从另一类补足。锚点只用于评估，执行与候选生成都不能读取；进入下一任务后，在候选生成和评估期间保持固定。

历史损失的计数是：

$$
D_n=\sum_{a\in A_n}\mathbf{1}\big[q(H_n,a)=1\ \land\ q(\widetilde H_{n+1},a)=0\big].
$$

它数的是“原来能做对、改后做错”的案例，其他案例的进步不会抵消这一损失。例如，视觉定位的 IoU 从 0.68 降到 0.41，跨过 0.5 的成功阈值，就增加一个损失。即便另一题从错误变正确，这个损失仍被计入。

$B_n=0$ 要求当前做对的锚点全部保留；$B_n=\infty$ 使历史损失不再阻止候选提交。有限的正数则允许每次更新造成少量锚点退步。这个预算控制每次提交，不是整个任务序列的累计遗忘上限。

附录 C 把各任务的成功标准具体化：问答使用规范化后的答案匹配，GSM8K 检查最终数值，视觉定位检查有效框与 IoU，ALFWorld 检查 50 步内是否达到目标，Minecraft 检查保留技能测试中的物品或世界状态条件。[对应§3.3.2、附录 A.1、附录 C](https://arxiv.org/html/2608.19013v1)

### 与传统持续学习的对应关系

§3.4 将这些机制与传统方法作概念性联系：原始经验保留与 replay 相近；经验抽象和技能提炼支持迁移；技能组织与调度有助于复用；评估门槛通过约束更新来控制干扰。这些是功能上的对应，论文没有宣称逐一实现了传统持续学习算法。[对应§3.4](https://arxiv.org/html/2608.19013v1)

## 实验设计与评分口径

同一实验内所有方法采用相同基础模型，模型在整个序列中冻结。不同场景使用不同模型，以覆盖不同模型家族和规模。

| 实验 | 任务序列与冻结模型 | 数据配置 |
|---|---|---|
| ALFWorld | 取放、光照观察、清洁、加热、冷却、双物体；Qwen3.5-9B | 每类 10 个适应回合；每回合最多 50 步；最终 134 个官方评估回合 |
| Minecraft | 收集、合成、采矿、放置、熔炼和多步依赖等 50 项；Qwen3.6-27B | 环境反馈用于适应；保留技能测试检查历史行为 |
| 文字推理主实验 | MuSiQue → ProofWriter → GSM8K → HotpotQA；DeepSeek-V4-Flash | 每任务 250 个适应、50 个验证、500 个测试样例 |
| 多模态主实验 | COCO 检测 → COCO 描述 → RefCOCO 定位 → VQAv2；Qwen3.6-27B | 每任务 250 个适应、50 个验证、500 个测试样例 |
| 文字历史预算扫描 | 同一文字顺序；DeepSeek-V4-Flash | 每任务 300 个适应、80 个验证、600 个测试样例；每个旧任务 80 个锚点；共 40 次提案机会 |
| 组件消融 | 同一多模态顺序；Qwen3.5-4B | 每任务 250 个适应、50 个验证、500 个测试样例 |

当前验证集和历史锚点只由评估器使用；独立测试集只用于报告成绩。最终平均表现是序列结束时各任务分数的平均；平均遗忘量是旧任务曾达到的最高测试分数减去最后分数，再对旧任务取平均。这个遗忘指标不等同于相对 Zero-shot 的差距。

Stability-HCL 和 Plasticity-HCL 分别使用 $B_n=0$ 和 $B_n=\infty$。主实验的离散指标要求至少多做对一个验证样例，连续指标要求指定得分严格提升，且不产生无效结果。独立的预算扫描则要求 80 个验证样例中至少多做对两个、格式合规率至少 90%，并且没有语法、工具或环境违规。两组阈值不能混用。

下列表格按论文报告的尺度列示；多模态任务使用各自指标，不能将所有分数都解释为同一种准确率。静态方法的遗忘栏标为“—”，表示没有序列更新，不是测得遗忘为零。[对应§4.1、附录 A.2](https://arxiv.org/html/2608.19013v1)

## 实验结果与解释

### ALFWorld 的能力获取与保留

| 方法 | 最终平均表现 | 平均遗忘量 |
|---|---:|---:|
| Static Harness | 47.12 | — |
| RAG | 55.56 | 1.74 |
| MemP | 53.15 | 5.18 |
| MemRL | 51.51 | 5.64 |
| Stability-HCL | 61.74 | 2.64 |
| Plasticity-HCL | 62.98 | 10.94 |

HCL 的最终平均表现高于这些对照。稳定型比静态 harness 提高 14.62 个百分点；可塑型提高 15.86 个百分点。这里是六类任务的宏平均，不能理解为 134 个回合全部混合后的成功率。

可塑型在最后的双物体任务达到 100.00，但旧任务遗忘更大；稳定型获得相近平均成绩并显著减少相对可塑型的遗忘。RAG 的遗忘量实际上低于稳定型 HCL，因此实验支持 HCL 的获取与保留权衡，不支持“稳定型 HCL 在所有方法中遗忘最少”。MemP 和 MemRL 是作者在统一框架中的复现版本。[对应§4.2.1、表 2](https://arxiv.org/html/2608.19013v1)

### Minecraft 的长期技能积累

HCL 完成全部 50 项任务，静态 harness 在 15 项后停滞。完成课程的累计环境动作数为 HCL 83、MemRL 88、MemP 91。结果支持经验、技能和流程复用能够帮助冻结模型推进更复杂的交互任务。

保护条件是当前目标改善，并继续通过适用的保留技能测试。附录明确指出，已完成任务没有在每次更新后系统性重跑，所以这里展示的是课程推进与技能级保留，不能当作完整的 50 任务遗忘测量。环境动作减少也不等于总计算成本更低，因为候选生成与评估仍需额外计算。[对应§4.2.2、图 3、附录 A.2](https://arxiv.org/html/2608.19013v1)

### 文字推理主实验

| 方法 | MuSiQue | ProofWriter | GSM8K | HotpotQA | 最终平均 | 平均遗忘 |
|---|---:|---:|---:|---:|---:|---:|
| Zero-shot | 35.00 | 42.80 | 49.40 | 54.80 | 45.50 | — |
| Stability-HCL | 27.60 | 73.00 | 50.40 | 57.80 | 52.20 | 0.00 |
| Plasticity-HCL | 29.00 | 77.00 | 92.00 | 60.80 | 64.70 | 0.07 |

主要提升集中在逻辑推理和可塑型的数学推理。但两种 HCL 的 MuSiQue 最终成绩都低于 Zero-shot。稳定型的遗忘量为零，仍可以同时出现相对 Zero-shot 更低的分数：遗忘指标比较的是这条 HCL 轨迹上旧任务的最好成绩与最终成绩，并不要求超过原始模型基线。[对应§4.3.1、表 3](https://arxiv.org/html/2608.19013v1)

### 多模态主实验

| 方法 | 检测 | 图像描述 | 视觉定位 | VQAv2 | 最终平均 | 平均遗忘 |
|---|---:|---:|---:|---:|---:|---:|
| Zero-shot | 4.27 | 25.47 | 43.00 | 84.87 | 39.40 | — |
| DGG | 29.58 | 29.77 | 48.96 | 62.60 | 42.73 | 0.26 |
| Plasticity-HCL | 64.14 | 37.31 | 90.60 | 79.80 | 67.96 | 0.81 |
| Stability-HCL | 65.34 | 39.41 | 91.60 | 79.33 | 68.92 | 0.22 |

提升主要集中在检测和定位。这些任务需要把空间信息组织成特定输出，harness 的输入处理与格式组织可能起到重要作用。VQAv2 上 Zero-shot 仍最好，说明整体平均进步不代表每个子任务都进步。在这组实验中，稳定型的最终平均略高、遗忘更低，说明历史保护不必然牺牲最终平均表现。[对应§4.3.2、表 4](https://arxiv.org/html/2608.19013v1)

### 历史损失预算的控制实验

| 每次更新预算 $b$ | 最终平均表现 | 平均遗忘量 |
|---|---:|---:|
| 0 | 61.25 | 0.39 |
| 1 | 63.46 | 1.22 |
| 3 | 62.04 | 2.00 |
| $\infty$ | 60.13 | 3.45 |

放松预算时，测得遗忘从 0.39 增到 3.45；最终表现却在 $b=1$ 达到最高，不是预算越大越好。作者提出的可能解释是：一些对当前任务有利的修改破坏了以后仍需要复用的经验或技能，影响后续演化路径。这是对机制的解释性假说，表格直接证明的是不同预算下的结果差异。

$b=0$ 仍有 0.39 的测试遗忘，清楚显示有限锚点的覆盖边界。这组实验的数据规模和提案配置与文字主实验不同，不能将其与表 3 的数字直接视为同一次运行。[对应§4.4、表 5、图 4](https://arxiv.org/html/2608.19013v1)

### 组件消融

消融禁用的是某个组件的更新；组件仍可参与执行，只保持初始化内容。结果如下：

| 配置 | 最终平均表现 | 平均遗忘量 |
|---|---:|---:|
| Zero-shot | 34.84 | — |
| 禁止接口更新 | 62.37 | 0.11 |
| 禁止记忆更新 | 62.28 | 0.83 |
| 禁止能力更新 | 63.12 | 0.06 |
| 禁止调度器更新 | 62.77 | 0.14 |
| Full HCL | 63.41 | 0.45 |

完整更新取得最高平均成绩，禁止接口或记忆更新的影响最大；禁止记忆更新还增加了遗忘。几个受限版本的遗忘反而更少，说明少改动可能同时减少获取与干扰，不能只凭遗忘小就认定系统更好。

这些消融差距总体较小，而且本节基于特定多模态序列。能力清单的贡献较小不能外推为“技能不重要”。附录中的提交次数也不能直接比较成接受率或更新效率，因为每次提交都会改变后续证据和提案轨迹。[对应§4.5、表 6、附录 B](https://arxiv.org/html/2608.19013v1)

## 证据边界与阅读判断

**有限锚点的保护范围。** 零历史损失只覆盖保留样例。即使模型冻结、锚点全部通过，其他旧任务仍可能退步。论文自身在 ALFWorld 和预算扫描中测到了这一现象。

**成功阈值与连续质量不同。** 历史损失使用二元成功指标。例如 IoU 从 0.9 降到 0.51 仍通过 0.5 阈值，不计作一个失败，但定位质量已经下降。这是从附录 C 的定义得到的分析，说明门槛保护的行为范围应与实际需求一致。

**任务顺序与搜索方式。** 方法按预定顺序修订组件，并保留当前阶段的最好备选。由此推测，它可能受顺序影响，也可能漏掉“单独修改不达标、联合修改才有效”的组合。这是搜索策略的潜在局限，不是论文已经用实验确认的结论。

**计算和统计证据。** Minecraft 的动作统计衡量执行动作，不覆盖全部优化开销。要选择真实系统方案，还需要总模型调用、token、时延和评估成本的同预算比较。正文表格没有呈现重复运行的方差或置信区间，因此对消融中的小幅差异应保留判断空间。

**复现细节。** 论文明确了更新对象、硬门槛和数据边界，但§3.3 中的综合排序权重、具体提示模板和若干搜索配置仍需要明确，才能复现完全相同的提交轨迹。

**持续适应与递归改进。** 更新后的 harness 会影响下一轮执行和下一轮改进证据，形成长期适应。但本论文没有展示优化器或评估器自身也被演化，不能据此声称改进机制会越来越强或改进速度会持续加快。[原文依据为§3.3、§4及附录；本节的机制局限为阅读分析](https://arxiv.org/html/2608.19013v1)

## 工程应用与并行扩展

把 HCL 用于实际 Agent 时，可借鉴的主要做法是：把提示词、记忆、技能和路由配置保存为可追溯的整体版本；让候选在隔离环境中运行；维护覆盖核心旧行为的检查集；同时测量获取、保留和运行有效性，再决定是否提交。运行经验库与评估锚点应分开，避免把用于检查的案例直接交给改进器。

如果目标是并行多路径演化，可从同一已部署版本复制出多个候选分支，让它们尝试不同修改方向，在统一条件下并行评估，再选择达标者。不同分支的修改若要合并，合并后的整套 harness 需要重新评估，因为单独通过的改动组合后仍可能互相干扰。还需要保存父版本、修改内容、评估结果和成本，以比较分支轨迹。

以上是从论文框架得到的工程扩展，论文实验没有验证并行分支、自动合并或分支档案。对于不同风险的任务，可以进一步采用不同历史预算或更严格的关键行为检查；这也属于应用设计，应独立评估效果。

## 论文结论与后续问题

作者在结论中强调，harness 可以在冻结模型周围积累能力、支持失败恢复，也会发生可测量的遗忘。把历史行为损失放进提交条件，能够调节这种获取与保留的关系。后续挑战包括更高效的历史评估、harness 内容整理，以及更长交互序列上的评测。

值得进一步验证的是：扩大或动态选择锚点能否改善覆盖；保护关键旧任务与平均表现之间如何取舍；相同计算预算下这套流程与多次尝试、单纯记忆检索的收益有何差别；以及并行搜索和联合组件修改是否能找到顺序策略漏掉的候选。这些问题影响方法能否从论文任务流推广到长期运行的真实 Agent。[对应§5；后续验证问题为阅读分析](https://arxiv.org/html/2608.19013v1)
