# AutoSaddler

论文：*AutoSaddler: Automatic Harness Optimization with Durable Updates from Agent Execution Traces*  
作者：Sungho Park 等  
版本：arXiv:2608.23041v1，2026 年 8 月 24 日  
阅读日期：2026 年 10 月 11 日  
原文：[arXiv HTML 全文](https://arxiv.org/html/2608.23041v1)

AutoSaddler 研究的是如何自动调试一个 AI agent 的工作方式：读取任务执行记录，定位失败原因，修改提示词、工具和运行流程，再用测试决定哪些修改值得保留。它优化的是模型外部的 harness，可以理解成 agent 的工作说明、工具箱和操作流程。论文报告的三个测试基准都取得了提升；最值得关注的发现是，可靠的改进既要修好失败任务，也要减少对原本成功任务的破坏。

## 研究问题与已有工作的关系

一个 agent 可能会推理、会调用工具，却仍然无法稳定完成长任务。安排会议要查日历、比较时间、创建事件、发送通知；其中任何一步出错，都可能导致整个任务失败。模型的能力、工具能做什么、规则是否清楚、运行流程是否合理，会共同影响结果。

人工调试 harness 需要反复阅读很长的日志，判断问题出在什么位置，再修改并测试。换一个模型或任务领域后，这些工作还可能需要重做。第 1 部分提出的问题是：能否把这种开发阶段的调试做成自动优化流程，并在有限的运行预算内找到更可靠的配置？

第 2 部分把 AutoSaddler 放在已有研究中理解。自动提示词优化提供了根据反馈修改文字规则的思路；自演化 agent 提供了利用历史经验的思路；harness 优化已经尝试直接修改系统代码；失败诊断研究关注如何从操作轨迹定位问题；演化搜索则启发系统组合不同候选版本的优点。

因此，这篇论文的贡献主要在于方法的组织方式：让深入诊断、限定修改范围、实际复测、开发集评估和历史版本选择共同工作。作者强调，补丁应当改善未来同类任务的表现，而不是只让触发修改的某一次执行成功。[原文第 1、2 部分](https://arxiv.org/html/2608.23041v1)

## 演化对象和评价目标

第 3 部分先划定研究边界。任务需要多步推理和工具交互，但任务之间假设彼此独立、不延续状态。这不妨碍单个任务内部存在状态变化，只是不把跨任务长期记忆纳入当前设置。

每次执行会产生两样东西：执行轨迹记录 agent 做过什么，最终结果用于判断任务是否完成。两者分别服务于诊断和评分。同一道任务即使使用同一套配置，也可能因模型采样、工具选择和环境交互而得到不同结果，因此一次成功不能证明配置稳定可靠。

论文允许修改三个部分。

| 修改对象 | 通俗解释 | 可能的修改 |
| --- | --- | --- |
| 提示词与指令 | 告诉 agent 应当如何工作 | 补充歧义处理规则，修改冲突的指令 |
| 工具及接口 | 决定 agent 能做什么、怎么调用 | 增加搜索工具，扩展过滤参数，修复工具实现 |
| 运行时控制逻辑 | 决定操作前后和任务循环如何运行 | 修改 hook、预处理步骤、预算提醒或循环逻辑 |

公式中的参数 θ 就是这三部分配置的集合，包括文字、接口和可执行代码。本文不更新模型权重，也没有把任务 agent 的记忆或技能库整理纳入优化空间。EvoDAG 保存的是优化过程的经验，这与任务 agent 的长期记忆是两个概念。

理想目标是在未来任务上获得更高的平均得分。这个平均既考虑不同任务，也考虑同一道任务的运行波动。如果任务评分是成功记 1、失败记 0，就可以把目标理解成整体成功率。实际只能用有限数据估计：先计算每道题重复运行的平均分，再对各道题取平均。

执行一个候选配置在一道任务上完整运行一次，称为一次 rollout。系统有有限的 rollout 预算，所以找到的是预算内探索过的候选中表现较好的版本。最终按照开发集成绩选版本，再用测试集报告结果；这不保证找到了所有可能配置中的全局最优解。[原文第 3 部分](https://arxiv.org/html/2608.23041v1)

## 一次失败如何变成下一版改进

第 4 部分给出开发阶段的优化循环：

当前版本执行一小批训练任务 → 诊断并打补丁 → 在同一批任务复测 → 有净提升时评估开发集 → 对比结果并记录经验 → 根据历史构造下一版。

诊断不是只让模型看完日志说一句失败原因。Diagnosis-Patch Agent 可以读取成功和失败的执行轨迹，也可以检查 harness 代码，逐步寻找证据并考虑其他可能原因。诊断和修改由同一个 agent 完成，让调查中发现的上下文直接参与补丁生成。

以文件建错目录为例，以下是说明方法的假设场景：agent 可能没有搜索目标目录，也可能搜索工具能力不足，或拿到了正确结果却忽略了它。前两种情况可能需要修改工具或路径处理逻辑，后一种情况可能需要调整规则。区分原因后，补丁才能落在有作用的位置。

修改范围有明确限制。优化 agent 只能编辑 harness 的功能代码，不能接触评测代码和基准数据。作者还把修改分为改变可执行能力的 Capability Patches，以及调整文字引导的 Steering Patches。搜索前期优先补工具与运行能力，后期再调整提示词、工具说明和提醒文字。这个安排是探索策略，不能保证文字修改的影响一定小。

补丁随后在同一小批任务上复测。只有修改后的总得分严格高于原来的总得分，才满足本轮接受条件。例如原来六道题成功三道，修改后修好两道、弄坏一道，成功数变成四道，净收益为正。

这里必须区分“本轮通过”和“最终有效”。本轮通过只是进入开发集评估的条件，并不要求开发集成绩也一定超过上一版。开发集结果会影响历史分析和后续选择；预算结束后，系统返回开发集得分最高的已评估候选，而不一定返回最新版本。

无论补丁被接受还是拒绝，Reflection Agent 都比较修改前后的结果和轨迹：哪些任务被修好、哪些退步、哪些仍失败、哪些仍成功，并解释修改的作用和副作用。失败尝试也有价值，因为它能帮助后续搜索避开相同问题。[原文第 4 部分](https://arxiv.org/html/2608.23041v1)

## 历史版本如何支持多路径演化

EvoDAG 是保存优化历史的有向无环图。每个节点对应一个探索过的 harness 版本，带有成绩、补丁说明和经验；连接记录版本之间的变化。Evolution Agent 读取这份历史，决定继续当前版本、返回更好的旧版本，或选择不同分支中有证据支持的补丁组合。

这类似一个保留实验结果的版本库。某个版本把搜索工具改好了，但加入的通用提醒又产生副作用，系统可以只取搜索工具的有效修改。不同版本如果各自修好了不同问题，也可以尝试组合，之后仍需执行新任务检验。

论文描述的是逐轮生成和评估候选的主循环。多路径指不同版本谱系可以保留、回退和重组；它没有把同时运行多个改进器的并行搜索作为核心算法。因此，不能仅凭 EvoDAG 的分支结构，把方法描述成多个 agent 同时沿不同路径演化。

“Improver”也不是本文定义的独立模块名。如果用它泛指改进器，可以理解为诊断打补丁、反思、版本演化三个 agent，加上评估循环和 EvoDAG，共同构成的优化系统。

附录 J 给出了一次具体搜索轨迹：第 20 轮出现严重回退后，系统回到较好的历史版本，挑选已验证的修改，随后第 27 轮达到 72.3% 的开发集峰值。这个例子说明历史记录能够帮助恢复和重新组合；72.3% 是开发集分数，不是最终测试集成功率。[原文第 4 部分与附录 J](https://arxiv.org/html/2608.23041v1)

## 实验结果与关键证据

第 5 部分覆盖三类任务：GAIA2 的模拟日常助手操作、SWE-Bench Pro 的软件工程任务，以及 Terminal-Bench 2.0 的终端操作任务。除特别说明外，实验使用 Claude Opus 4.6。训练、开发和测试来自不同任务组；例如软件任务用不同代码仓库划分，检验配置能否推广到新仓库。

主结果使用 Pass@1，也就是一次尝试的任务成功率。表 2、表 3 报告最终测试阶段三次运行的均值；三次运行用于估计一次尝试表现的波动，不是把三次尝试中任意一次成功记为成功。主实验通常只做一次优化搜索，这与最终测试重复三次需要区分。

| 基准 | 对应初始 harness | 初始成功率 | AutoSaddler 成功率 | 提升 |
| --- | --- | --- | --- | --- |
| GAIA2 | Default Agent | 53.0% | 62.0% | 9.0 个百分点 |
| SWE-Bench Pro | SWE-agent | 37.3% | 46.9% | 9.6 个百分点 |
| Terminal-Bench 2.0 | Terminus 2 | 40.0% | 50.0% | 10.0 个百分点 |

按表中的均值计算，AutoSaddler 相比各基准最强的自动基线，分别高出 7.4、4.4、6.7 个百分点。这里的改进是总体成绩提升，并非所有任务组都最佳：例如 SWE-Bench Pro 的 Element-web 子集，GEPA 为 45.2%，AutoSaddler 为 43.5%。

消融实验更能解释哪些设计有用。作者拆掉某个环节，再观察 GAIA2 测试表现。

| 实验设置 | GAIA2 成功率 | 相对完整方法的变化 |
| --- | --- | --- |
| 完整 AutoSaddler | 62.0% | 基准 |
| 换成浅层诊断 | 57.8% | 下降 4.2 个百分点 |
| 去掉结构化干预 | 56.9% | 下降 5.1 个百分点 |
| 去掉面向泛化的选择 | 50.6% | 下降 11.4 个百分点 |

浅层诊断只用一次模型调用读取轨迹和评分后推断原因。去掉结构化干预后，91.5% 的补丁集中在文字引导上，工具和运行能力的探索明显减少。去掉面向泛化的选择则同时取消反思与开发集评估，不能把全部下降归因于其中某一个模块。

最后一项尤其值得重视：50.6% 低于初始配置的 53.0%。进一步分析发现，完整方法和该消融版本修好旧失败任务的能力相近，差距主要在于消融版本更容易弄坏原本成功的任务。改进器需要判断修改的影响范围，才能保住已有能力。

附录 G 还比较了补丁类型：能力修改的修复率为 55%、回退率为 8%；文字引导修改的修复率为 58%、回退率为 17%。这些是本次搜索中生成补丁的统计结果，支持能力修改可能更稳定的解释，但不足以推断所有代码修改都会优于提示词修改。

效率方面，GAIA2 上 AutoSaddler 用约 1,000 次总任务执行达到 72.3% 的开发集准确率，GEPA 和 Meta-Harness 在约 2,800 次执行后分别达到 64.6% 和 61.5%。论文另用 147 条学习轨迹说明信息利用效率；147 条轨迹与约 1,000 次总执行是不同口径。优化器每次生成补丁的费用也不一定更低，效率优势主要来自更有选择地调用昂贵的任务评估。[原文第 5 部分、表 2、表 3 与附录 G、I](https://arxiv.org/html/2608.23041v1)

## 结果能够支持什么判断

论文的证据支持：在这些有明确评分的任务环境中，自动优化 agent 外部配置可以带来可观提升，深入诊断、限制修改方式和开发集选择都对效果有贡献。第 6 部分据此把自动 harness 优化视为提高长任务可靠性的一条可行路线。

我的解读是，方法最值得借鉴的部分是它对修改副作用的处理。系统既收集修复证据，也记录回退、失败尝试和版本关系，让下一轮有依据地选择和重组。这使“看起来合理的建议”必须接受实际效果检验。

这些实验还不能证明 agent 会无限持续进步，也不能保证迁移到任意真实工作环境。任务评分、可复现的环境、测试预算和版本管理，共同构成了当前效果成立的条件。[原文第 5、6 部分](https://arxiv.org/html/2608.23041v1)

## 局限与值得继续追问的问题

最直接的限制是任务结果必须容易判断。作者假设训练任务有正确答案或清晰的成功指标。真实工作中，“这封邮件是否合适”“这份研究是否有价值”往往很难自动评分；如果反馈不可靠，优化过程也可能朝错误方向改进。附录 R 将弱监督和无监督的反馈作为未来方向。

当前任务之间彼此独立，方法尚未覆盖跨任务长期状态、记忆和技能整理。把它迁移到持续工作的个人助手时，还要解决任务相互影响、环境变化和历史状态的问题。实验主要基于 Claude 系列模型；论文虽提供跨模型迁移的结果，但更广泛的模型适用性仍需验证。

从评估角度看，最终测试重复三次有助于观察运行波动，但不等于反复进行了完整优化搜索。主实验通常只有一次搜索，附录 C 补充了一次独立运行；优化搜索本身的稳定性仍值得关注。另一个值得继续验证的问题是，长期反复用同一开发集选版本，会在多大程度上使搜索适应该开发集。这是对方法的进一步分析，不是论文已经证实发生的结论。

真实落地时，最需要优先建立的是可信的评分和复测环境。保存更多日志、增加更多候选，只有在能够判断净收益和副作用时，才有明确的改进意义。[原文第 5.1 部分与附录 C、R](https://arxiv.org/html/2608.23041v1)
