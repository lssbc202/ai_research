# RSI

**论文**：*The Last AI Built by Humans: Toward Genuine Recursive Self-Improvement*  
**版本**：arXiv:2609.11873v3  
**阅读日期**：2026年10月12日  
**原文**：[HTML全文](https://arxiv.org/html/2609.11873v3) · [PDF](https://arxiv.org/pdf/2609.11873v3)

## 一 核心判断

这篇论文是一份围绕递归自我改进（RSI）的综述与研究路线图。它尝试回答：AI究竟接管了改进过程中的哪些决定，哪些变化能够留到下一轮，以及有什么证据说明系统真的变好了。

理解全文，最重要的是分清三件事：**这次任务做得更好、执行任务的系统变得更好、负责改进系统的方法变得更好。** 三者都可能带来分数上涨，但只有最后一项直接触及作者在L5强调的元改进。

论文最有价值的贡献，是要求沿着完整的改进过程检查证据：谁提出修改，谁验证，什么被保留，下一轮是否使用，以及改进是否经得起独立评测和成本核算。它还明确区分了“改进机制发生变化并被复用”和“新版机制确实更会产生有效改进”。[§1.7](https://arxiv.org/html/2609.11873v3#S1.SS7)

**本报告的评价是：这套分析问题的方法，比把系统硬塞进某个等级更有用。** 作者将B0至L5写成责任逐步转移的层级，但L2、L3、L4在机制与案例上存在明显交叉；不能简单理解为每升一级，就新开放一类组件的修改权限。现有证据也不足以普遍证明系统能在相近资源下，多代稳定提高自身的改进效率。

## 二 全文的行文逻辑

引言从AI开发的三类负担出发：基础模型开发需要大量资源和工程协调；持续学习需要不断生产有用经验并可靠评判；部署以后又要反复诊断问题、修改系统、验证和发布。

这些负担首先说明自动化有价值。作者进一步追问：能否把组织这些改进的部分能力保留在系统内部，让本轮的成果帮助下一轮改进？这个问题才引向RSI。**成本高是研究动机，并不能单独推出“必须递归自我改进”或者“必须由同一个模型修改自己”。**[§1.1—1.2](https://arxiv.org/html/2609.11873v3#S1.SS1)

| 章节 | 在全文中的作用 |
|---|---|
| 第1章 | 提出开发负担，说明为什么要研究可持续的自主改进，提出继承、自主权归属和验证问题 |
| 第2章 | 给出能力背景、改进循环的基本概念，以及分析系统与证据的口径 |
| 第3章 | 用B0—L5组织已有方法，讨论各类自主决定及其验证方式 |
| 第4章 | 比较科学、具身智能、软件和医疗中的反馈条件与应用限制 |
| 第5章 | 展示企业实践中实际修改、保存和复用的内容 |
| 第6章 | 汇总持续改进尚未解决的研究与工程问题 |
| 第7章及附录 | 收束路线图，提供文献分布、产业索引和应用领域的详细案例 |

### 第2章提供能力背景和分析方法

§2.1用不同领域的基准成绩说明能力进步并不均衡，为后文关注交互任务、工具使用和持续适应提供背景。作者先处理不同来源和评测协议，再用HCI表示相对基准进入年份前沿，关闭了多少剩余分数空间。它是一个基准归一化指标，不能直接读成“AI已经具备百分之多少的真实能力”。

其中，2026年之后的延伸采用统一比例填补剩余空间，属于示意性设定，**不是RSI实验已经测得的效果，也不是经过验证的预测**。这部分展示研究潜力，不能用于证明RSI的有效性。[§2.1](https://arxiv.org/html/2609.11873v3#S2.SS1)

§2.2转而建立全文真正的分析单位：一个可追踪的改进循环。§2.3解释为什么同时纳入论文、技术报告、工程材料和企业资料；相应地，不同来源的结果也需要保留各自的证据强度。

## 三 用A与B理解系统和改进机制

为方便解释，本报告沿用两个角色。**这是阅读辅助记号，不是论文规定的唯一系统架构。**

- **A是执行任务的对象系统**，可以是模型、带工具和工作流的Agent，或者包含记忆、技能和运行框架的完整任务系统。
- **B是负责改进的机制**，包括诊断问题、产生候选修改、组织实验、评估候选和保留更新等功能。实际实现可以由多个模型、程序和人工环节共同承担。

A与B可以共享模型，也可以分开部署。关键是功能和信息如何跨轮传递，而不是组件在物理上是否装进同一个模型。

论文对几个容易混淆的概念有如下区分：

| 概念 | 含义 | 与A和B的关系 |
|---|---|---|
| 改进对象 target | 这一轮直接修改的东西 | 通常是A的某个部分，也可以变成B的搜索程序或评估器 |
| 改进器 improver | 根据当前状态和经验产生候选修改的机制 | 是B中的核心功能 |
| 策略 strategy | 改进器如何安排搜索、决定从哪里修改和怎样生成候选 | 是改进器采用的方法，不必是独立Agent |
| 验证器 verifier | 评价候选并执行接受规则的机制 | 可以是测试、模型判断、形式检查或人工评价的组合 |
| 后继 successor | 继承了已接受修改、继续下一轮的系统 | 需要实际使用继承状态，而非仅存档 |

把策略理解为Agent使用的skill，有助于建立直觉，但策略还可能写在代码、提示词、采样规则、选择规则或研究政策中，不能限定成skill文件。[§2.2.1](https://arxiv.org/html/2609.11873v3#S2.SS2.SSS1)

完整过程可以写成人话：**从任务中得到反馈，提出修改，按规则验证，保留通过的修改，让下一轮从修改后的状态开始。** 在论文的操作性定义中，“改进”首先指被接受和继承的修改；它是否带来真实、持续的能力收益，还需要另外证明。

分析前必须先确定系统边界。同一份代码既可能只是本次交付的产品，也可能是下一轮继续优化的系统状态。不能仅凭文件是否保存、Agent是否运行很久，判定发生了自我改进。更强的RSI主张还要检查：继承的变化是否影响以后产生、评估、选择或积累改进的方法。[§2.2.1—2.2.3](https://arxiv.org/html/2609.11873v3#S2.SS2)

## 四 B0至L5的定义和边界

### 作者希望表达的责任转移

| 档位 | 作者强调的内容 | 最需要检查的证据 |
|---|---|---|
| B0 | 在当前任务内反复修改、验证或选择输出 | 任务结束后，没有留下供未来独立任务使用的系统变化 |
| L1 | 执行人规定的改进流程 | 接受的修改进入系统状态，并在之后复用 |
| L2 | 根据反馈，自主选择下一种改进方案 | AI承担“下一步值得试什么”的决定，而不仅执行指定步骤 |
| L3 | 根据当前能力，自主安排后续学习内容 | 能力变化影响经验选择，学习又影响更后面的选择 |
| L4 | 根据持续运行反馈，让系统持久适应 | 经验转成记忆、技能、代码等修改，并影响后续执行 |
| L5 | 改进机制本身成为修改对象 | 新版改进器、评估器或研究政策被继承，并参与后续改进 |

这张表概括作者的组织意图。§3.7明确采用“逐步转移改进责任”的叙述，而不是按某一种算法或某一种文件来分级。[§3.7](https://arxiv.org/html/2609.11873v3#S3.SS7)

### B0和L1的定义明确 但部分L1案例需要补全系统边界

定义上的分界是持久性：B0只改善当前任务输出，L1要求修改进入后续任务或轮次。L1并不要求B自己进化，也不要求底层模型参数改变。

§3.2开头的Meta Capacity Efficiency例子展示了明确的采用过程：AI按预定排障程序执行，产出的PR经审核和集成，成为生产系统的持久改动。这里保留的是生产系统的修改，不能自动改述为执行Agent学会了新技能。

§3.2还覆盖数据处理、训练方法、训练平台、评测、部署和应用开发。其中有些例子清楚展示了一个AI辅助环节，却未在同一段描述中完整展示“修改进入哪个系统、下一轮怎样继承”。因此，不能仅凭“AI在做AI研发任务”就独立判定为L1，也不能为了匹配等级而替案例补出不存在的学习步骤。附录B使用了“相关实践”“使能组件”“候选”等限定标签，也提醒读者不要把所有条目当作完整等级认证。[§3.1—3.2](https://arxiv.org/html/2609.11873v3#S3.SS1) · [附录B](https://arxiv.org/html/2609.11873v3#Ax2)

### L2和L3存在概念包含与机制交叉

选择训练数据、安排练习任务，本来就可以是一种改进策略。L2的定义没有禁止这样做。L3专门强调的是：当前学习者的变化，持续影响下一轮学习内容。

所以，不能用“是否发现短板”“是否根据反馈调整”区分二者，两者都能做到。按广义的改进策略理解，L3所讨论的机制已被涵盖；作者将这一责任单独列出，是分类上的强调。固定的选样算法只要依据变化中的学习者状态作决定，也可以具备L3机制，无须改写选样器本身。作者也提醒，本节展示的局部机制不能单独决定整个系统的最高等级。[§3.3—3.4](https://arxiv.org/html/2609.11873v3#S3.SS4)

### L4不等于新增修改记忆或技能的权限

L2已经可能修改Agent的技能、提示词和harness，并保存改进；L3也已经包含环境交互和持久技能。因此，这些都不是L4独有的条件。

作者把L4的重点放在持续运行中的适应：从实际任务反馈中提炼并验证长期修改，检查它们能否在后续任务、不同环境和执行模型下继续发挥作用。更新可以实时进行，也可以离线批量提炼后再使用，不能简单把L3和L4解释成离线与在线的区别。**本报告判断，L2与L4更多体现研究场景和关注点的差异，难以据此建立互斥的组件权限表。**[§3.5](https://arxiv.org/html/2609.11873v3#S3.SS5)

### L5的关键是修改以后负责改进的方法

按A与B的典型分工，L4可以由方法不变的B不断给A增加技能；L5还要求负责生成、评估或选择后续改进的机制发生持久变化，并实际接管以后的改进。

固定B看到新反馈后提出不同方案，仍可能只是执行同一个方法。判断L5需要指出具体被继承的程序、提示词、评估机制或研究政策，以及它怎样控制了后续改进。A和B可以共享代码，部分案例也会同时改变多个组件；因此，要看功能和后续作用，不能只按代码属于哪个目录判定。[§3.6](https://arxiv.org/html/2609.11873v3#S3.SS6)

## 五 L1至L4的代表性技术

### L1把已有流程中的专业工作交给AI执行

这一部分横跨AI开发流程，§3.2.1至3.2.6是工作环节，不是六个新增自主等级。例如，FineWeb-Edu用模型产生教育质量标注，再训练分类器扩大筛选规模；EDIT依据预定诊断信号定位并修订推理步骤；HealthBench让模型应用专家制定的评分规则；AIPC以技能和阶段验证组织部署适配。

这些方法的价值在于自动完成需要语义判断的工作。它们不只是把已有批处理脚本运行一遍，但目标、流程和接受标准仍主要来自外部。某个环节产生了有用结果，与完整系统形成了跨轮改进，仍需分别检查。[§3.2](https://arxiv.org/html/2609.11873v3#S3.SS2)

### L2让AI根据实验结果选择下一种改法

| 工作 | 实际技术点 |
|---|---|
| GEPA | 读取执行轨迹和失败反馈，定位提示词应修改的部分，并保留互补候选 |
| ADAS | 把Agent表示为可执行程序，让元Agent生成、验证并保存不同设计 |
| AFlow | 把工作流表示成可执行图，通过蒙特卡洛树搜索探索修改路径 |
| AgentSquare | 将可复用模块进行演化与组合，把成功结构作为后续设计材料 |
| AgentNAS | 由LLM提出任务相关的初始架构及搜索空间，再进行候选搜索 |
| autoresearch与AutoKernel | 根据实测结果反复修改训练程序或GPU内核，验证效果后保留候选 |

这些工作的共同价值，是把“看完失败以后，下一次值得试什么”部分交给系统。接受标准和外层搜索框架可以仍然固定。更大的搜索空间并不自动带来更高效率，反复接触评测也可能导致过拟合或利用漏洞。[§3.3](https://arxiv.org/html/2609.11873v3#S3.SS3)

### L3让学习内容跟着学习者变化

这里的任务主要用于训练或练习，不是用于最终独立验证泛化能力。它关注的联系是：当前能力影响练习选择，练习形成持久学习，再影响以后选择。

| 工作 | 下一轮学习内容如何受当前能力影响 | 需要保留的限定 |
|---|---|---|
| AZR | 同一模型提任务和解题，依赖当前解题能力的奖励引导后续出题，执行器检查任务与解答 | 可执行验证与学习价值是两个问题 |
| R-Zero | 根据当前Solver多次回答的一致性，给Challenger不确定性反馈 | 不一致不一定是有益难度，一致也不保证正确 |
| STP | 当前证明器能证明但较困难的猜想训练出题者，经过检查的证明训练证明器 | 不是专挑当前完全无法解决的题 |
| PSV | 根据Solver给出的难度标签生成规格，并验证生成程序是否满足规格 | 实际难度存在重叠，满足规格不等于值得学习 |
| VOYAGER | 当前状态与探索历史影响目标选择，成功行为进入技能库并支持以后探索 | 持久能力可在外部技能库，无须更新LLM权重 |
| SIMA 2的完整ASKA设置 | 专门任务安排模块根据能力评估，把练习分配给弱项 | 固定任务上的自生成轨迹实验本身不能证明任务选择自主 |
| SEAgent | 从轨迹与界面变化更新软件指南，再据此生成后续练习 | 错误指南可能持续误导探索 |

评测时，应把自适应安排与固定安排或只读取旧学习者状态的版本比较，并匹配数据来源和总预算。题目正确、难度合适、训练后有收益，不能互相替代。[§3.4.2—3.4.4](https://arxiv.org/html/2609.11873v3#S3.SS4.SSS2)

### L4把运行经验变成可长期使用的修改

这一部分可以按修改的生命周期理解：从记录里产生候选经验，修改执行系统，验证是否接纳，再检查长期使用情况。

| 工作 | 具体留下什么 | 值得关注的技术 |
|---|---|---|
| ACE | 文字经验条目 | 记录条目是否有帮助，以局部增补代替反复重写整份记忆 |
| APEX | 包含任务里程碑和前置条件的策略图 | 记录路径结果，也保留尚未尝试的分支供规划选择 |
| Trace2Skill | 可移植技能目录 | 分别分析成功与失败轨迹，合并技能修改，供后续Agent加载 |
| Metis | 文字记忆与可调用工具 | 将反复使用的计划转成代码，通过检查后进入工具库 |
| DecoEvo | 解题skill与评分规则生成skill | 分开两者的反馈，检查规则覆盖和区分能力，减少评分放宽带来的假进步 |
| HarnessDev | 候选harness | 固定执行模型，在隐藏任务上比较成功率和执行成本 |
| HDSO | 通过验证的新技能 | 先提出假设和验证计划，在同样任务上比较有无候选技能，再到独立任务确认 |
| Library Drift | 持续维护的技能库 | 跟踪贡献、限制活跃数量、适时退役；过度淘汰也可能损害效果 |

本节一个重要发现是：能写出有用更新，与执行Agent能用好更新，是不同能力。错误可能出现在经验归纳、适用范围判断、检索激活或执行过程；只看最终总分无法区分。保存过的经验，也必须随着任务和模型变化重新检查。[§3.5.1—3.5.4](https://arxiv.org/html/2609.11873v3#S3.SS5.SSS1)

## 六 L5怎样改进B本身

### 修改候选生成和搜索程序

这里的搜索，是在不同代码、策略和系统修改方案中寻找有效候选，不是搜索网页。搜索程序决定怎样生成候选、探索哪些分支、怎样选择结果。

**STOP**把改进器B的Python源代码作为优化目标。候选B可能采用不同的束搜索、采样或选择逻辑；它们的质量通过“能把其他程序改得多好”来衡量。选中的新版B负责下一轮自我改进。这个例子清楚展示了改进程序成为被继承对象。

**Gödel Agent**把任务策略与递归更新逻辑共同开放给修改，下一次调用执行新版程序。开放范围更广，也意味着不良修改可能被继承。

**DGM**保存编码Agent变体并探索后代，但档案管理和父代选择仍在自修改范围之外。作者将它作为过渡案例，不能直接把任务分数提高当成整个搜索机制变强。

**HyperAgents**明确开放任务Agent与元Agent代码。演化出的元Agent会用性能追踪和持久记忆指导修改，并表现出一定跨任务迁移；但更长的200轮实验没有证明迁移初始化在最终结果上具有统计显著优势。[§3.6.1](https://arxiv.org/html/2609.11873v3#S3.SS6.SSS1)

### 修改决定保留谁的评估器

**RQGM**处理的是一个两难：固定评估器可能被反复搜索找到漏洞，评估器随时改变又会使分数不可比。

它在一个阶段内冻结评估器，到预定边界再用独立真实标准检验候选评估器；选中的版本接管下一阶段。旧评估器产生的相关分数作废，之后重新考察受影响的Agent时再评分。关键不只是“评分工具升级”，而是升级后的机制实际参与选择未来后继版本。独立参照、替换安排和调度仍固定在外部。[§3.6.2](https://arxiv.org/html/2609.11873v3#S3.SS6.SSS2)

### 修改后续研究遵循的政策

**A-Evolve-Training**让Worker进行训练实验，Collector汇总结果，Meta-agent修订研究政策，供下一轮Worker使用。政策保留当前训练方案、继续或放弃的方向以及失败方法记录。

原文的具体情况是开发分数上涨，但外部表现没有改善。系统随后调整实验方向，允许尝试改善外部目标、即使降低原代理分数的方案。作者把这种持久政策的修订和复用也纳入机制改进，不要求所有改进都必须写成新的优化器源码。总体任务目标和基本约束仍由外部确定。[§3.6.3](https://arxiv.org/html/2609.11873v3#S3.SS6.SSS3)

### 自动做研究与更会改进研究助手仍需分开

Meta AIRA 2和Anthropic Automated Alignment Researchers展示了自动实验和研究输出，但本节认为其公开结果尚未建立研究程序被修改并继承的完整证据。

Weco AIDE 2更进一步，让研究Agent改进研究Agent的harness。公司报告了接受的更新和迁移效果；然而，把演化后的助手安装为外层改进器后，未观察到统计显著的搜索效率优势。这正说明“新版Agent做研究更好”和“新版Agent更会继续改进自己”需要不同实验。[§3.6.4](https://arxiv.org/html/2609.11873v3#S3.SS6.SSS4)

## 七 怎样评估一项RSI主张

论文对L5区分两种证据：**结构性L5**证明改进机制被修改、保留并用于后续；**有效L5**还要证明新版机制在可比预算和独立评价下，能产生或选出更好的后继。

用A与B表达，一次公平的检查应让旧B和新版B从可比的A与实验信息出发，给予匹配预算，然后比较它们产生的结果。迁移测试中可以固定新版B，让它改进新的A，以检查此前获得的方法能否复用；固定B不等于停止改进A。[§3.6.5](https://arxiv.org/html/2609.11873v3#S3.SS6.SSS5)

综合全文，可将审查过程整理为以下问题。这是本报告对论文分析口径的归纳，不是作者另行提出的一套等级。

1. **系统边界是什么**：哪些是任务产物，哪些属于会被继承的系统状态？
2. **变化具体写到哪里**：模型参数、提示词、技能、工具、harness，还是B的改进政策？
3. **谁决定修改和接受**：AI、固定算法、专家，分别控制哪些步骤？
4. **下一轮是否真正使用**：有无版本、调用、检索或行为证据，不能只看是否存档？
5. **效果是否可靠**：新任务能否迁移，旧能力有无退步，评测是否被反复优化或利用漏洞？
6. **收益是否划算**：生成候选、实验、验证、开发改进器、人工审核和维护的总成本是多少？
7. **B是否更有效**：若声称元改进，是否直接比较新旧B，而非仅展示A的成绩？

多轮研究还需要记录失败更新、最大退步、恢复过程和停止条件。自主权范围、任务能力收益、改进效率是三个独立维度；更多自动化并不能替代其中任何一项效果证据。

## 八 应用领域怎样改变验证条件

第4章没有提出新的等级，而是说明相同的改进循环放到不同领域后，反馈的成本和可信度会改变。

| 领域 | 反馈和可继承内容 | 主要限制 |
|---|---|---|
| 科学研究 | 实验结果推动假设生成方法、研究工具和技能变化 | 失败可能来自假设、协议或仪器；有效性依赖假设与条件 |
| 具身智能 | 行动轨迹推动策略、世界模型、技能或课程变化 | 感知、规划、控制、硬件问题难区分；真实试错代价高 |
| 软件工程 | 执行与回归测试支持代码、harness和经验继承 | 测试覆盖不完整，难以代表全部用户意图与维护要求 |
| 医疗 | 专家反馈、指南和诊断证据支持记忆、流程与工具更新 | 结果延迟且受多种因素影响，现有证据以模拟和回顾性研究为主 |

这一章反复强调：优化出一个更好的分子、程序或诊断结果，并不能单独证明产生它的AI系统得到持久改进。必须继续追踪经验如何进入后续任务使用的组件；若声称元改进，还要追踪负责改进的机制。[第4章](https://arxiv.org/html/2609.11873v3#S4)

## 九 八个工业案例留下了什么

第5章最适合按“什么被留下，下一轮怎样使用”阅读。以下效果沿用论文记录的企业报告口径，不将内部评估视为独立复现。[第5章各案例](https://arxiv.org/html/2609.11873v3#S5)

| 案例 | 可复用的内容与技术点 | 证据应怎样解读 |
|---|---|---|
| Theseus | 整理工作环境，再构想把任务困难转成训练数据，训练模型后继续改善环境 | 实验主要证明固定模型与harness受益于环境整理，完整共同演化仍待建立 |
| Lark | 企业知识图谱、自动质量判断和错误归因，让数据修正进入后续迭代 | 数据基础与诊断改善有内部证据，人仍制定标准并审核重要更新 |
| 小红书 | 快路径更新结构化用户记忆，慢路径将审核过的难例用于后训练 | 初步推荐评分收益不能直接解释为点击率或转化率提升 |
| Humanlaya | 跨批次反馈更新质检规则、提示词、示例和技能，验证后替换质检版本 | 明确展示质检系统的持久更新；不单独证明其外层改进器更强 |
| ModelBest | 项目内生成并实测工程实现，项目间复用优化方法、参考实现和失败经验 | 工程实测与人力估计要分开，不能把估计当成受控人机对照 |
| 腾讯混元Hyra | 保存代码、产物、日志、分数与反馈，重组经验支持并行探索，并可修订评估器 | 任务成绩与评估机制修改是不同证据，不能直接推成递归效率提高 |
| Agent-Native Research Lab | 可执行研究资料包保存代码、规格、失败分支与原始证据，结果可从日志核对 | 支持知识继承与复现，保存更完整不自动等于B发生自修改 |
| Frontis | 专业Agent负责业务，改进Agent积累并复用跨任务诊断、修改与验证经验 | 分别测专业Agent表现和改进效率，后者仍是企业内部报告 |

### Humanlaya把修任务和改系统的区别讲得最具体

它的内环检查并修复当前交付的数据包；外环汇总不同批次的错误，修改以后检查数据的方法。

原文案例中，提取工具无法解析一个扫描PDF，质检Agent就把文档判成不可用。人工确认文档本身清晰后，系统产生区分“工具提取失败”与“文档质量差”的规则和示例。经留出样本验证、人工审核后，这些修改进入下一版本，用于以后的任务。

公司报告，在相同底座模型、工具和处理预算下，用600个未参与更新的任务包比较V0与四次更新后的V4：自动修复后仍含关键缺陷的任务包比例从9.0%降至3.7%，平均人工处理时间从每项48分钟降至27分钟。这个比较同时关心质量和人力，能够支持质检系统改善；它没有单独隔离新版B的改进能力。[§5.4](https://arxiv.org/html/2609.11873v3#S5.SS4)

### Frontis尝试分别评价A与B

Frontis的专业Agent对应A，负责改进的MA对应B。系统既保存改好的Agent，也保存问题背景、诊断理由、候选修改、验证结果和适用条件，供以后改进其他Agent时复用。

公司报告，在使用相同评估器的76项可比任务上，专业Agent平均分从5.25升至5.87；另外，在积累100多项任务的元改进经验后，未见过的内部测试任务上的改进过程，相对不使用跨任务经验的流程约快20%。前一个数字描述A，后一个才试图描述B的效率。它们不能混用，也尚不是独立复现结果。[§5.8](https://arxiv.org/html/2609.11873v3#S5.SS8)

## 十 论文的贡献与局限

**第一，论文把关注点从“用了什么技术”转到“改进究竟怎样发生”。** 同样使用记忆或代码修改的系统，可能在决策权限、继承方式和验证质量上完全不同。沿完整循环分析，比仅凭技术标签判断更有解释力。

**第二，论文把递归结构与实际效果分开。** 改进器被修改并调用，是结构证据；它能否在同样预算下更有效地产生下一代，则是效果证据。这一要求可以过滤不少仅展示任务分数上升的强叙事。

**第三，工业案例补充了单次实验不容易看到的环节。** 数据质量、经验版本、人工审核、回归测试、旧技能维护和发布成本，都直接决定改进能否持续运行。

局限也比较明确。其一，L2至L4的定义和实例存在交叉；把自主责任、应用场景和持久更新机制放在同一条等级轴上，会让相邻边界不够清楚。其二，有些条目展示的是改进流程中的一个组件，读者需要自行检查完整系统边界和继承证据。其三，企业报告、技术材料和学术实验的证据强度不同，汇总在同一张图或表中不代表可直接比较。

这些是对框架适用范围的评价，不意味着所有分类都任意。B0与持久系统更新的概念区分，以及L5对机制修改、继承和复用的要求，仍提供了有用的审查问题。更稳妥的用法是先描述具体机制和证据，再把等级作为辅助标签。

## 十一 后续研究和阅读索引

第6章的八个方向可以合并为四项工作：准确定位应修改的组件并获取真正有用的学习经验；确保保留的内容被正确使用并适应不同领域的验证要求；可信地修改B并证明长期收益；核算全部资源与人工成本，同时保存下一轮可以复查、复现和继承的研究记录。[第6章](https://arxiv.org/html/2609.11873v3#S6)

第7章将论文定位为以自主权为中心的路线图。它把持续提高“改进能力”作为目标，同时要求在明确资源约束、独立评估和人类控制边界下，通过长期实验建立证据。[第7章](https://arxiv.org/html/2609.11873v3#S7)
